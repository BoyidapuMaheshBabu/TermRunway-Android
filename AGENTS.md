# TermRunway Android — Codex Engineering Instructions\n\n## 1. Mission\n\nTermRunway Android is a native Android student-finance application built to help students understand where their money goes and how their money changes over time.\n\nThe product must feel like a real, dependable mobile application, not a demo screen or a collection of disconnected features.\n\nPrimary engineering goals:\n- clear and predictable user flows\n- professional, consistent Android UI\n- correct financial calculations\n- reliable local data persistence\n- responsive state-driven UI\n- maintainable architecture\n- testable business logic\n- safe handling of dates and money\n- incremental development with small, reviewable changes\n\nThe repository is an AI-assisted development project. AI may implement code, but every change must remain understandable, testable, and reviewable.\n\n## 2. Current Product Direction\n\n### Current scope\n\nDaily Tracking is the active product scope.\n\nDaily Tracking should support:\n- first-run/setup experience\n- home dashboard\n- income tracking\n- expense tracking\n- transaction creation\n- transaction editing\n- transaction deletion\n- date/day navigation\n- calendar date selection\n- recent activity\n- period summaries\n- category spending breakdowns\n- local backup and restore\n- settings/preferences\n\n### Next major scope\n\nTerm Mode / Plan Tracking will be developed only after the Daily Tracking foundation is stable.\n\nTerm Mode is intended to support:\n- fixed start and end dates\n- expected income\n- planned expenses\n- actual income and expenses\n- planned-vs-actual comparisons\n- remaining financial runway\n- status/health indicators\n- useful recommendations based on the user's actual situation\n\nDo not mix incomplete Term Mode functionality into Daily Tracking unless a task explicitly requires shared infrastructure.\n\n## 3. Product Principles\n\n1. Offline-first. The current product does not require a server, login, cloud database, Firebase, Supabase, or external API.\n2. Local ownership of data. User financial records remain local in the current product. Backup/restore must be explicit and safe.\n3. Financial correctness before visual polish. A beautiful screen with incorrect money calculations is a bug.\n4. Real-world UX. Important actions need sensible loading, empty, success, validation, and error states where applicable.\n5. Progressive complexity. Prefer a simple architecture that can grow. Do not add abstractions only because they look enterprise-like.\n6. Consistency. Reuse established components, spacing, typography, shapes, colors, iconography, and interaction patterns.\n7. Accessibility and usability. Respect readable text sizes, touch targets, content descriptions, contrast, keyboard behavior, and screen-state clarity.\n\n## 4. Technical Baseline\n\nUse the existing repository as the source of truth.\n\nCurrent baseline:\n- Kotlin\n- Jetpack Compose\n- Material 3\n- Android Studio / Gradle\n- application namespace: com.termrunway.app\n- minSdk: 24\n- target/compile SDK: use the versions already configured in the repository unless a task explicitly changes them\n\nBefore changing dependencies or build configuration:\n1. inspect the existing version catalog and Gradle configuration\n2. determine whether the needed capability already exists\n3. prefer existing dependencies\n4. add a dependency only when the requirement cannot reasonably be implemented with the current stack\n5. explain the reason in the change summary\n\nDo not casually upgrade Android, Kotlin, or Compose versions while implementing product features.\n\n## 5. Architecture Rules\n\nFollow separation of responsibilities.\n\nPreferred conceptual layers:\n\n### Presentation\nCompose screens, reusable UI components, navigation, UI state, and user events.\n\n### Domain\nBusiness rules and financial calculations that should not depend on Android UI.\n\n### Data\nModels, repositories, local persistence, backup/restore, and serialization.\n\n### Utility\nDate handling, currency/money formatting, parsing, and narrowly scoped helpers.\n\nThe exact package structure may differ from this description. Inspect the repository before creating files. Do not reorganize the whole project merely to match this document.\n\n### Repository boundary\n\nPersistence should be accessed through a repository/data boundary rather than directly from every screen.\n\nIf the existing project already has TermRunwayRepository, preserve and improve that pattern rather than creating a competing persistence mechanism.\n\nUI code should not contain large blocks of business calculations or raw persistence logic.\n\n## 6. Data and Financial Rules\n\nMoney is a high-risk data type.\n\nDo not use floating-point arithmetic for persisted monetary values when a safer representation is available in the existing architecture.\n\nUse a consistent monetary representation across:\n- transaction amount\n- income totals\n- expense totals\n- planned amounts\n- remaining amounts\n- dashboard calculations\n- chart values\n- backup/restore\n\nDefine and test rounding behavior.\n\nDates must use a consistent date representation and timezone strategy. Do not rely on implicit device timezone conversions when a date-only value is required.\n\nEvery calculation must define behavior for:\n- zero income\n- zero expense\n- no transactions\n- expense greater than income\n- income received after expenses\n- negative/invalid user input\n- empty periods\n- custom date ranges\n- same start/end date\n- future dates\n- deletion/editing of historical transactions\n\nNever silently clamp or hide financially meaningful values just to make a UI look nicer.\n\n## 7. Core Dashboard Concept\n\nThe dashboard should communicate the student's current financial situation quickly.\n\nThe current product direction includes:\n- available/current money\n- income and expense activity\n- recent transactions\n- clear status indicators\n\nFor Plan/Term calculations, the intended conceptual formula is:\n\nAvailable Money Now + Expected Future Income - Remaining Planned Expenses = Projected Remaining Runway\n\nThe final implementation must use the approved domain model and test the formula against edge cases.\n\nDo not hard-code a percentage or health value merely to make the UI look complete.\n\n## 8. TermRunway Financial Graph\n\nOne important future graph communicates the user's financial journey over time.\n\nGraph meaning:\n- red line = expenses/spending over time\n- yellow/orange line = savings or remaining spending balance over time\n- green dots = income received events\n\nThe graph is a timeline, not three unrelated decorative series.\n\nGraph rules:\n- X-axis represents time/date.\n- Y-axis represents money.\n- Expense and savings/balance series follow the selected date range.\n- Income is represented as discrete received events.\n- Income events use the actual transaction date.\n- Values come from real stored records.\n- Do not invent sample financial data in the production UI.\n- Tooltips/labels should make each series understandable.\n- The graph must remain useful with sparse data.\n- Empty states should explain what the user needs to record before the graph becomes meaningful.\n- If multiple income events occur on the same date, define deterministic display behavior.\n\nPreserve the visual meaning of the three series even if the charting library or rendering technique changes.\n\n## 9. UI/UX Quality Standard\n\nTarget the quality level expected from a polished consumer Android application.\n\nThis does NOT mean copying WhatsApp, Amazon, or another product. It means applying professional product-development standards.\n\nUI expectations:\n- clear visual hierarchy\n- intentional spacing\n- consistent corner radius and component shapes\n- predictable navigation\n- clean typography\n- meaningful icons\n- sensible animations only where they help\n- proper disabled/error states\n- empty states with useful guidance\n- no accidental layout jumps\n- responsive layouts\n- keyboard-safe forms\n- touch targets suitable for mobile use\n- dark/light theme behavior where supported by the existing design\n\nDo not add excessive gradients, decorative cards, random colors, unnecessary animations, or visual noise.\n\nFinance-related screens should feel calm and trustworthy.\n\n## 10. Design System\n\nBefore introducing a new UI pattern:\n1. look for an existing component\n2. reuse it if appropriate\n3. extend the shared component if the pattern is genuinely reusable\n4. create a screen-specific component only when reuse would make the design or code worse\n\nCentralize meaningful design decisions in the existing theme/design system where practical.\n\nCommon elements that should remain visually consistent:\n- primary action buttons\n- secondary actions\n- transaction cards/rows\n- amount display\n- section headers\n- status indicators\n- navigation\n- form fields\n- dialogs/sheets\n- date controls\n- empty states\n\nColor semantics should remain stable:\n- red communicates expense/outflow\n- yellow/orange communicates savings/balance trend\n- green communicates income received\n\nDo not use these colors inconsistently for unrelated meanings.\n\n## 11. Navigation and State\n\nNavigation should represent user intent, not implementation details.\n\nAvoid passing large mutable objects through navigation routes when an ID/key and repository lookup can provide the required data safely.\n\nUI state should be derived from observable application state where practical.\n\nAvoid:\n- duplicated source-of-truth state\n- unnecessary global mutable state\n- business logic hidden inside composables\n- side effects triggered accidentally during recomposition\n\nMake side effects explicit and lifecycle-aware.\n\n## 12. Transaction UX\n\nAdding an income or expense should be fast and understandable.\n\nA transaction editor should make these concepts explicit:\n- transaction type\n- amount\n- category\n- date\n- optional note/details where supported\n\nValidation must provide clear feedback.\n\nExamples:\n- missing amount → explain what is required\n- zero/invalid amount → reject according to the product rule\n- malformed numeric input → recover without crashing\n- invalid date → prevent an invalid record\n\nEditing must preserve transaction identity and update calculations correctly.\n\nDeletion should require an intentional user action and refresh all dependent summaries.\n\n## 13. Persistence, Backup, and Restore\n\nThe current product is local-first and JSON-based.\n\nPersistence changes must maintain compatibility with existing stored data whenever practical.\n\nWhen evolving the JSON format:\n- prefer explicit fields\n- avoid ambiguous field names\n- consider backward compatibility\n- validate data before replacing local state\n- do not partially restore a backup\n\nRestore behavior should be transactional from the user's perspective:\n1. read the backup\n2. validate the complete payload\n3. parse every required record\n4. reject invalid/incomplete backups safely\n5. replace local data only after successful validation\n\nNever destroy valid existing data because a backup file is malformed.\n\n## 14. Testing Requirements\n\nEvery meaningful feature should have tests appropriate to its risk.\n\n### Domain/business logic\nTest totals, date ranges, balances, runway calculations, percentages/health calculations, edge cases, expense-greater-than-income scenarios, and editing/deleting effects.\n\n### Persistence\nTest save, load, update, delete, empty state, backup, restore, and invalid restore input.\n\n### UI\nAdd Compose/UI tests for important user flows where practical. At minimum, protect high-value flows from regressions.\n\nAlways run the narrowest relevant tests first, then broader tests/build checks.\n\nPrefer deterministic tests over timing-sensitive tests.\n\n## 15. Verification Loop\n\nFor each implementation task:\n1. inspect the existing code\n2. understand the requirement\n3. identify the smallest safe change\n4. implement it\n5. format/compile as appropriate\n6. run relevant tests\n7. inspect errors/warnings\n8. fix regressions\n9. review the diff\n10. summarize exactly what changed\n\nDo not declare a feature complete merely because the code compiles.\n\nFor UI work, verification should include real-device testing when the change affects layout, navigation, keyboard/input behavior, gestures, date selection, scrolling, chart rendering, system bars, or device-specific behavior.\n\n## 16. Git Workflow\n\nKeep commits small and meaningful.\n\nPreferred pattern:\nfeature branch → implementation → tests → review → pull request → merge to main\n\nGood commit messages describe the change, for example:\n- feat: add transaction editor validation\n- feat: add daily spending summary\n- fix: handle expenses greater than income\n- test: cover runway calculation edge cases\n- refactor: extract transaction repository logic\n\nDo not mix unrelated refactors with a feature unless required.\n\nNever remove working behavior without understanding why it exists.\n\n## 17. Codex Working Rules\n\nWhen assigned a task:\n\n### First inspect\nRead the relevant source files and existing architecture before making changes.\n\nDo not assume the repository matches this document exactly.\n\n### Then implement\nMake the smallest coherent change that satisfies the requirement.\n\nPrefer extending existing patterns over introducing parallel systems.\n\n### Then verify\nRun the relevant Gradle tests/build tasks and inspect the result.\n\n### Then report\nThe final task summary should include:\n- what changed\n- important files changed\n- tests/build commands run\n- whether verification passed\n- known limitations or follow-up work\n\nDo not claim tests passed if they were not run.\nDo not claim real-device verification if it was not performed.\n\n## 18. Scope Discipline\n\nDo not introduce these into the current product unless an explicit requirement approves them:\n- Firebase\n- Supabase\n- cloud databases\n- authentication\n- external AI APIs\n- remote backend services\n- unnecessary analytics SDKs\n- unnecessary third-party charting/dependency additions\n\nThe application should remain usable without internet access.\n\nDo not add a chatbot or AI assistant to the current scope. AI/chat functionality is a later product direction and must not become an accidental dependency of the core financial application.\n\n## 19. Recommended Build Roadmap\n\n### Phase 0 — Repository Foundation\nGoal: understand and stabilize the existing codebase.\n- inspect current architecture\n- establish package boundaries\n- establish theme/design system\n- establish models\n- establish repository/data boundary\n- identify current technical debt\n- add/repair foundational tests\nExit criteria: project builds, architecture is understandable, core data flow is documented in code, and there are no unnecessary duplicate storage paths.\n\n### Phase 1 — Daily Tracking Core\nGoal: make the primary tracking loop dependable.\n- transaction model\n- add income\n- add expense\n- validation\n- edit\n- delete\n- selected date/day\n- daily totals\n- persistence\nExit criteria: user can complete the entire transaction lifecycle offline, data survives app restart, and calculations remain correct after edits/deletes.\n\n### Phase 2 — Professional Daily Tracking UX\nGoal: move from functional UI to polished product UX.\n- onboarding/setup\n- home dashboard\n- recent activity\n- date navigation\n- calendar selection\n- reusable transaction components\n- empty states\n- validation/error states\n- responsive forms\n- theme consistency\n- accessibility pass\nExit criteria: common flows feel intentional and consistent, with no obvious placeholder/demo behavior.\n\n### Phase 3 — Daily Insights\nGoal: help users understand spending behavior.\n- 7-day view\n- 30-day view\n- 90-day view\n- category totals\n- income totals\n- expense totals\n- period comparisons\n- useful empty states\nExit criteria: period boundaries are correct, insights are derived from real transactions, and calculations are covered by tests.\n\n### Phase 4 — Financial Timeline Graph\nGoal: visualize the user's financial journey.\n- time-based expense line\n- savings/balance line\n- income event dots\n- selected period\n- tooltips\n- sparse-data behavior\n- empty state\n- performance check\nExit criteria: graph accurately reflects stored data and the red/yellow-or-orange/green meanings remain consistent.\n\n### Phase 5 — Backup and Restore\nGoal: protect user data.\n- JSON export\n- JSON import\n- schema validation\n- safe restore\n- invalid-backup handling\n- compatibility strategy\nExit criteria: valid backup round-trips successfully and invalid backup never destroys valid local data.\n\n### Phase 6 — Plan/Term Tracking Foundation\nGoal: add the second major product mode on top of stable shared infrastructure.\n- plan model\n- start/end dates\n- expected income\n- planned expenses\n- actual activity integration\n- remaining planned amounts\n- projected runway\n- plan status\nExit criteria: plan calculations are deterministic and tested, and Daily Tracking remains unaffected.\n\n### Phase 7 — Plan UX and Decision Support\nGoal: make the plan mode useful for real student decisions.\n- planned-vs-actual views\n- health/status indicators\n- spending guidance\n- runway visualization\n- future income handling\n- expense > income scenarios\n- custom plan periods\nExit criteria: users can understand the relationship between plan and reality without reading documentation.\n\n### Phase 8 — Quality Pass\nGoal: make the application production-like.\n- regression tests\n- accessibility review\n- performance review\n- crash-prone input review\n- state restoration review\n- backup compatibility review\n- dark/light theme review\n- small-screen review\n- physical-device regression pass\n- code cleanup\nExit criteria: no known critical workflow regressions, tests protect financial calculations, and UI and architecture are maintainable.\n\n## 20. Definition of Done\n\nA feature is done only when:\n- requirement is implemented\n- happy path works\n- relevant edge cases are handled\n- state/persistence behavior is correct\n- UI has empty/error/disabled states where needed\n- tests are added or existing tests adequately cover the behavior\n- build/test verification was run\n- diff has been reviewed\n- no unrelated behavior was changed accidentally\n\nTermRunway should be built brick by brick, with each brick tested before the next major feature is placed on top.
